## 2. Decided differently from the specs, and why

**Postgres, not Upstash Redis.** Phase 1 opens with a stated assumption —
"the game currently persists nothing server-side (ghosts and medals are
localStorage)" — and an offer: "If leaderboards already hit a backend, tell me
and I'll rewrite Phase 1 to use it instead of standing up a second one." The
assumption is false. `runs`, `players` and `worlds.play_count` have been here
since the first week. The counters are four new tables in the same Neon
database: no new service, no `UPSTASH_*` variables, one fewer outage to design
around. Redis was chosen in the spec for atomic `INCR`; `UPDATE ... SET plays
= plays + 1` is atomic for the same reason, and `ON CONFLICT DO NOTHING` on a
composite primary key does the like-dedupe that `SADD` was wanted for.

**`src/content/registry.ts` is written out by hand and imports nothing.** The
spec asks for one file everything downstream reads, and is right. Deriving it
from `CABINETS` / `PARKOUR_COURSES` / `SANDBOX_WORLDS` would have pulled
twenty-one course-geometry builders into any API route that only wanted to
validate a slug. So it is a literal list, and `registry.test.ts` asserts it
holds exactly those three registries' slugs, titles and taglines. It cannot
drift; it can only fail the suite, with the missing slug named.

**No stats badge on the two mode cards.** A badge helps somebody choose
between many similar things. There are two modes, they are the largest thing
on the page, and nobody ranks them against each other by play count.
`race-mode` is still *counted*, so it can appear in Popular this week;
`parkour-mode` is not, because it is a course picker and the twenty-one
courses behind it count themselves.

**Fixed hourly rate-limit buckets, not sliding windows.**
`Ratelimit.slidingWindow` is an Upstash primitive. One upsert per request
against `rate_hits`, keyed by a SHA-256 of the caller, the route and the hour.
The approximation costs two hours' budget spent across a boundary, against a
budget of thirty plays — not a distinction a popularity sort can feel.

**The footer totals line is fetched, not server-rendered.** This one is worth
reading twice. An async server component in the footer builds fine and the
route table still prints `○ Static` beside all seven pages that carry it —
because the query runs once, at build time, and its answer is baked into the
HTML. The line would then show the numbers as of the last deploy, forever, and
nothing about it would look wrong. Social proof frozen at build time is worse
than none. It is `GET /api/stats/totals`, cached five minutes, fetched after
paint at the bottom of the page where nothing moves when it lands.

## 3. What was fixed on the way through

- **Every card had to stop being one big `<a>`.** A `<button>` inside an `<a>`
  is invalid HTML; browsers disagree about which one a press activates and a
  screen reader reads the button's label as part of the link's name. Cards are
  now a container with a stretched link (`.card-linked` / `.stretched-link` /
  `.card-actions`), so the whole tile is still one press and the heart is a
  real, separately focusable button. A headless pass confirms zero nested
  interactive elements anywhere on the site.
- **The content counts in the prose were wrong.** `/about` said "five parkour
  courses" when twenty-one ship. The root meta description and the home
  headline said twenty. `/parkour`'s own description said twenty while the
  paragraph directly beneath it — which reads `PARKOUR_COURSES.length` — said
  twenty-one on the same screen. All five now interpolate `COURSE_COUNT` /
  `CABINET_COUNT`, and a test pins those to the shipped content.
- **`/about` described the editor while `UGC` is off.** Now gated on the flag,
  as the home page's copy already was.
- **Two permanent eslint warnings.** `eslint-config-next` ships
  `no-unused-vars` with no ignore pattern, so the codebase's own `_difficulty`
  convention was being followed and warned about simultaneously. Two permanent
  warnings make "lint is clean" stop meaning anything.
- **A dead filter chip.** "Multiplayer" has been on exactly one entry since
  the arena was cut. It stays readable on the race card and is never offered
  as a chip: `filterTagsFor` computes chips per grid and requires two matches.
- **`AdSlot` reserves a height.** Both slot ids are empty so nothing renders
  today. The reservation is there so that the day a slot id is pasted in is
  not the day CLS regresses — which on this site is a revenue question.

## 4. What is not done

**Phase 3 entirely** — nine parkour courses, three race tracks, four cabinets,
three worlds. This is the content half of the spec, it is weeks of work, and
the spec is explicit that it must not be batched: "Nine courses, three tracks,
four cabinets and three worlds landing together is unreviewable and
unrevertable."

**Two slug collisions to settle before Phase 3 starts.** The spec proposes a
race track `spiral` and an expert course `gauntlet`. Both names are already
taken — Spiral Yard (Easy) and The Gauntlet (Hard), both shipped 7 September —
and a slug is the stats key, so it must be globally unique and permanent.
Renaming an existing one abandons its plays and likes. The new content needs
different slugs; `registry.test.ts` fails loudly if a duplicate is added.

**`blockyard-spec.md` §1, performance.** The live Real Experience Score of 46
has not been re-measured. Several of that spec's items are already true here
and were before this work: the game bundle is code-split and the engine is
behind `dynamic(..., { ssr: false })`, every loop is `requestAnimationFrame`
on a fixed timestep with a clamped delta, fonts are self-hosted through
`next/font` with `display: swap`, images go through `next/image`, and a
service worker caches the shell. What is genuinely open:

- Rapier's inlined wasm is ~1.1 MB gzipped and is the load. Prefetched from
  the menus; a direct `/race/<code>` link has nothing to prefetch from.
- Physics and collision are on the main thread. The spec's Web Worker item is
  a real architectural change, not a tuning pass.
- The AdSense script is `async` in `<head>` deliberately — the verification
  crawler reads the served HTML, and `next/script`'s afterInteractive strategy
  injects after hydration where it will not see it. Deferring it further is
  the spec's advice and would risk the thing it is there for. That trade
  should be made by the owner, not assumed.

**`blockyard-spec.md` §2, animation.** Largely already built and documented in
CLAUDE.md: the juice rules, `lib/motion.ts` as the single reader of
`prefers-reduced-motion`, hit-stop through the frame gate, one easing and
duration scale in `tokens.css`. No pass was made.

**`blockyard-spec.md` §3, offline.** Not built. Worth noting that its
`GameStateAdapter` describes a remote-first game, and this one is already
local-first where it counts — personal bests, arcade saves and settings are
`localStorage`, and only leaderboards, coins and published worlds need the
network. The genuinely useful pieces would be a health check with an "Offline"
indicator so a player knows why a board is empty, and a queue so a personal
best set on a train posts when the connection returns. The server side of that
is already safe: run submission compares times in SQL and refuses a slower
write, so a late-arriving stale run cannot overwrite a better one.

**A visual check of the 3D screens.** The headless browser has no GPU, so
`/play` and `/race` remain unverified by anything but a person.

## 5. Ship steps

1. **Apply the migration.** `npx drizzle-kit migrate` runs
   `0006_game_stats.sql` — four `CREATE TABLE`s and two indexes. Nothing
   existing is altered. Until it runs every counter reads as an em dash and
   nothing else changes, which was verified by running the whole site against
   the unmigrated database.
2. **Optionally set `NEXT_PUBLIC_DISCORD_INVITE`** in Vercel production. The
   invite in `lib/discord.ts` is used when it is unset, and a value that is
   not an https discord.gg / discord.com URL is rejected in favour of it.
3. Nothing else. No new dependencies, no pinned versions touched, no new
   service, no other new environment variables.
